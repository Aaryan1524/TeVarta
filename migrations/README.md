# Database migrations

T05 provides revision `0001`: all 21 frozen §5.1 tables plus `event_claims`
and `usage_records` for evidence and usage persistence. PostgreSQL 16 and pgvector
0.8.6 are the tested baseline. The server must have pgvector available; the
migration enables its `vector` extension. No `create_all` path is used.

## Apply or preview

Install the project with `make backend-install`. Supply `TEVARTA_POSTGRES_URL`
explicitly through the selected environment's secret/configuration mechanism.
The migration command does not load `.env` files or choose a default database.

```sh
export TEVARTA_POSTGRES_URL=postgresql://localhost/tevarta_dev
make database-upgrade
.venv/bin/python -m alembic current
.venv/bin/python -m alembic upgrade head --sql
```

The final command only prints reviewable SQL. Existing T06 environment separation
and credential rules apply. No deployed database was migrated as part of T05.
The API continues to serve mock fixtures until its persistence tasks land.

## Test against disposable databases

```sh
docker run --detach --name tevarta-database-tests \
  --publish 127.0.0.1:55435:5432 \
  --env POSTGRES_HOST_AUTH_METHOD=trust --env POSTGRES_DB=tevarta_test \
  pgvector/pgvector:0.8.6-pg16-bookworm
export TEVARTA_TEST_POSTGRES_URL=postgresql://postgres@localhost:55435/tevarta_test
make database-test
```

Trust authentication is only for this isolated localhost test container. Never
use it for shared/deployed databases. Tests require a local `tevarta_test`
connection with database-creation permission; they create random per-run databases
and delete only those databases in teardown. Existing schemas are never reset.
The fixture in `fixtures/database/foundation.sql` is entirely synthetic.
Ordinary backend tests skip database integration when the test URL is absent;
`make database-test` fails immediately without it. The `Database / migrations`
CI job supplies a disposable PostgreSQL service and runs the real tests.

## Storage boundaries

- Users, devices, articles and events have internal UUID primary keys and unique
  public IDs matching T03's `usr_`, `dev_`, `art_`, `evt_` forms. Persistence
  adapters resolve public IDs at the API boundary; they must never cast a public
  ID to UUID. `events.merged_into` remains a UUID foreign key as frozen in §5.1.
  Entity IDs remain text. Public IDs are generated by future application writers.
- `user_seeds` keeps the frozen composite key, weights, three source values and
  reverse index. This implements §5.1; it does **not** record SC4 founder agreement
  or add broker account/holding tables. Final SC4 sign-off is still pending.
- All seven named relevance measurements must be numeric and present, including
  the four with zero scoring weight. Shadow score and rank are also mandatory.
  No default invents those measurements.
- Users own devices, seeds, feed rows, feedback and notification logs; deleting a
  user cascades only through those rows. Events, evidence and world entities
  survive. Endpoint authorization, encryption of token values and lifecycle
  races are later tasks; a BYTEA column alone does not encrypt a token.
- Feedback stores the frozen telemetry action names plus the existing T03 aliases
  `impression`, `click`, `dismiss`; the ingestion boundary must normalize aliases
  before analytics. Card actions require event/slot context, app-level actions
  can omit it, and session-length actions require duration. Retry dedupe uses
  `(user_id, idempotency_key)`; separate actions get separate keys.
- `event_claims` links each compiled claim/revision to a real article. Event
  revision increments and transactional merge side effects belong to T28–T33;
  foreign keys do not implement a merge algorithm or prevent every merge cycle.
  T30 must validate that each article belongs to the event's evidence set and that
  the revision was actually issued; these foreign keys establish existence only.
- Usage rows bridge T06 quantity/unit/cost and T04 invocation metadata, with one
  row per `(request_id, component)`. Producers use a fresh request ID per actual
  invocation/attempt. This schema does not persist T06's in-memory budget ledger
  or implement cross-worker cap enforcement.

## Rollback and future revisions

`alembic downgrade base` deletes all T05 application tables and their data.
Use it only on disposable development databases or through an approved recovery
plan with backups. The rollback retains pgvector and refuses to cascade into
unknown dependent objects. Upgrade/downgrade/re-upgrade is covered by tests.

Keep revision `0001` and its SQL immutable after merge. Add new revisions with
`alembic revision -m 'describe change'`; there is no ORM metadata/autogeneration
contract yet. Do not modify API model definitions to represent database rows.
